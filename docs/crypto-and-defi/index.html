    Blockchain #

    A blockchain is a shared, append-only database maintained by many computers in a network, in which transaction data is grouped into blocks and each block cryptographically references its parent, so that altering past data requires redoing all subsequent blocks and network consensus.
    Intuition: Think of it as a public ledger copied onto thousands of computers: everyone holds the same history, and no single party can quietly rewrite it.
    Mechanics: Transactions are batched into blocks; each block contains a hash of the previous block, chaining them together. Nodes independently verify every new block against consensus rules, and a consensus mechanism (e.g. proof-of-work or proof-of-stake) decides which blocks extend the canonical chain.
    Failure modes: A 51% attack or consensus failure can reorganize recent blocks, reversing transactions; software bugs in dominant client implementations can halt or split the chain.
    Misconceptions: Blockchains are not inherently immutable at the tip — recent blocks can be reorganized, which is why confirmations or finality matter. Not every blockchain is decentralized or permissionless; private chains exist.
    Example: If you send ETH to someone, the transaction is included in a block; on proof-of-stake Ethereum, after roughly two epochs (~13 minutes) the block containing it is finalized and cannot be reverted without at least one-third of staked ETH being destroyed.
    Aliases: block chain

    Distributed ledger #

    A distributed ledger is a database that is replicated, shared and synchronized across multiple nodes or institutions, with updates agreed through a consensus process rather than written by a single central administrator.
    Intuition: Instead of one bank keeping the master copy of the books, every participant keeps an identical copy and they all agree on each new entry.
    Mechanics: Each node holds a copy of the ledger; new records are propagated through the peer-to-peer network and accepted only if they satisfy the protocol's validation and consensus rules. A blockchain is one specific form of distributed ledger that orders records in cryptographically chained blocks, but DLT also includes non-block structures (e.g. DAGs, permissioned ledgers).
    Failure modes: If the consensus layer or validator set is compromised or centralized in practice, the ledger can be censored or rewritten despite nominal distribution; poor network connectivity can partition the ledger into divergent views.
    Misconceptions: 'Distributed ledger' and 'blockchain' are not synonyms — all blockchains are DLT, but distributed ledgers need not organize data in blocks or be public. Distribution of copies does not by itself guarantee distribution of control.
    Example: Ethereum's ledger of accounts and smart-contract state is stored and updated by every node in the network, so two independent nodes reading the same finalized block compute the same balances without trusting each other.
    Aliases: DLT, distributed ledger technology

    Consensus mechanism #

    A consensus mechanism is the complete stack of protocols, incentives and ideas that allows a distributed network of nodes to agree on a single state of a blockchain, including Sybil resistance, block author selection and a chain-selection (fork-choice) rule.
    Intuition: It is the rulebook that lets thousands of strangers agree on one version of history without a referee.
    Mechanics: A Sybil-resistance component (e.g. proof-of-work's energy expenditure or proof-of-stake's locked capital) makes it costly to fake identities; a block-production protocol selects who proposes and validates blocks; and a fork-choice rule (longest/heaviest chain) resolves competing versions. Economic rewards and penalties align honest behavior.
    Failure modes: If an attacker obtains 51% of hash power or a large share of stake, they can censor or reorder transactions and, below finality thresholds, reorganize the chain; bugs in the fork-choice rule can cause chain splits.
    Misconceptions: Proof-of-work and proof-of-stake alone are not complete consensus mechanisms — they are Sybil-resistance and block-author-selection components inside one (e.g. Ethereum's Gasper combines Casper-FFG with LMD-GHOST).
    Example: On Ethereum, consensus is reached when validators representing at least two-thirds of total staked ETH attest to checkpoint blocks, at which point those checkpoints are justified and then finalized.
    Aliases: consensus protocol, consensus algorithm

    Proof of work #

    Proof of work (PoW) is a Sybil-resistance and block-author-selection mechanism in which miners compete to find a nonce that makes a block's hash fall below a difficulty target, expending real-world computation; the chain with the most accumulated work is treated as canonical.
    Intuition: Miners burn electricity on a lottery; the winning ticket lets them write the next page of the ledger, and cheating would require out-computing the whole honest network.
    Mechanics: Miners repeatedly hash a candidate block header with different nonces until the hash meets the target set by the difficulty parameter; difficulty retargets to keep average block time constant. Validity is cheap to verify but expensive to produce, and the longest (most-work) chain rule resolves forks.
    Failure modes: An attacker controlling a majority of hash rate can double-spend by mining a private chain that outpaces the honest one; mining-pool centralization and hardware/energy concentration erode the security model.
    Misconceptions: PoW does not 'solve a useful puzzle' — the computation is deliberately useless work whose only purpose is to be costly. High hash rate secures history but does not increase transaction throughput.
    Example: In Bitcoin, miners increment a nonce until the block hash has the required number of leading zero bits; at ~10-minute block targets, an attacker trying to reverse a 6-block-deep transaction must redo that work and then outpace all honest miners, an economically prohibitive task.
    Find nonce n such that H(block_header(n)) <= T, where T = target set by difficulty (lower T = harder); probability per hash ≈ T / 2^256 (SHA-256).
    Aliases: PoW

    Proof of stake #

    Proof of stake (PoS) is a Sybil-resistance and block-author-selection mechanism in which validators lock capital (stake) that can be destroyed (slashed) for dishonest behavior, and are pseudo-randomly selected to propose and attest to blocks.
    Intuition: Instead of proving you burned electricity, you post a bond: misbehave and your bond is burned, so cheating costs you directly.
    Mechanics: In Ethereum's PoS, a validator deposits 32 ETH, runs execution, consensus and validator clients, and is randomly selected to propose blocks in 12-second slots while committees attest each epoch. Casper-FFG finalizes checkpoints backed by ≥2/3 of staked ETH; equivocation or contradictory attestations are slashable.
    Failure modes: An attacker with >1/3 of stake can stall finality, and with a majority can steer the fork choice; long-range attacks and weak subjectivity require checkpoints; staking-pool centralization can concentrate effective control.
    Misconceptions: PoS does not pay interest for 'locking money in a bank' — rewards pay for active validation duties, and downtime or misbehavior incurs penalties. Staked capital is not risk-free yield.
    Example: A user deposits 32 ETH into the Ethereum deposit contract, joins the activation queue, and then attests every epoch (~6.4 minutes); if they propose two blocks in the same slot, part of their stake is slashed and they are ejected.
    Aliases: PoS

    Validator #

    A validator is a node participant in a proof-of-stake network that has deposited stake and is responsible for checking new blocks, attesting to the head of the chain, and occasionally proposing new blocks, earning rewards for honest work and penalties or slashing for failures or misbehavior.
    Intuition: A validator is like a juror with money on the table: it votes on what the true chain is, and loses money if it lies or sleeps.
    Mechanics: On Ethereum, a validator is activated by depositing 32 ETH into the deposit contract and running execution, consensus and validator clients. Each 12-second slot one validator is chosen to propose a block and committees attest; attesting and proposing correctly yields ETH rewards, while being offline leaks stake and equivocation is slashed.
    Failure modes: Correlated misbehavior (mass slashing) can destroy large fractions of stake; client monoculture means a bug in a majority client can cause correlated penalties across the network; key compromise lets an attacker get the validator slashed.
    Misconceptions: Running a validator is not passive income — it requires uptime and correct signing, and offline validators steadily lose ETH. Staking through a pool still carries the underlying validator risks.
    Example: A validator that stays online and attests correctly earns roughly a few percent APR on its 32 ETH; one that is slashed in an isolated incident loses about 1 ETH immediately plus additional penalties over a 36-day forced exit.

    Miner #

    A miner is a network participant in a proof-of-work blockchain that expends computation to find valid block hashes, collecting new coins (block subsidy) and transaction fees in exchange for extending the chain.
    Intuition: Miners are the bookkeepers of a PoW chain who pay for their write access with electricity instead of collateral.
    Mechanics: Miners gather transactions into a candidate block and repeatedly hash its header with varying nonces until the hash meets the difficulty target; the first to succeed broadcasts the block and earns the block reward (new issuance plus fees). Difficulty retargets so that, regardless of total hash rate, blocks arrive at a target interval.
    Failure modes: Miners controlling a majority of hash rate can censor transactions or execute double-spends; falling coin price with fixed energy costs can force miners offline (miner capitulation), temporarily reducing network security.
    Misconceptions: Miners do not 'create bitcoins out of nothing' — issuance follows the protocol's fixed schedule, and mining revenue competes away toward energy costs. Mining does not verify your personal transactions faster; it secures the whole chain probabilistically.
    Example: A Bitcoin miner that finds a valid block currently earns the block subsidy (3.125 BTC after the 2024 halving) plus the fees of all included transactions, roughly every 10 minutes on average across the network.

    Node #

    A node is any computer running blockchain client software that connects to peers, propagates transactions and blocks, and verifies data against the protocol's consensus rules.
    Intuition: Every node keeps its own copy of the ledger and checks the math itself — 'don't trust, verify'.
    Mechanics: Full nodes download and validate every block and re-execute transactions, pruning old state; archive nodes additionally retain all historical states; light nodes download only block headers and request proofs from full nodes. On Ethereum a node pairs an execution client (EVM/state) with a consensus client (proof-of-stake).
    Failure modes: If most users rely on a few hosted node/RPC providers, the network re-centralizes in practice even with many independent nodes; a bug in a dominant client can take down a large share of the network simultaneously.
    Misconceptions: Running a node does not by itself earn rewards — only miners (PoW) or validators (PoS) are paid. A light node trusts block headers and does not fully verify state.
    Example: An Ethereum full node stores recent state (typically the last 128 blocks), verifies every new block against consensus rules, and serves data to light clients and wallets via its RPC endpoint.
    Aliases: full node

    Wallet #

    A wallet is an application or device that manages a user's cryptographic keys and uses them to view balances, sign transactions and interact with blockchain applications; the assets themselves live on the ledger, not inside the wallet.
    Intuition: A wallet is a keychain plus a window into the blockchain, not a purse that 'holds' coins.
    Mechanics: Wallets generate and store private keys (often derived from a seed phrase), derive public addresses, and sign transaction requests that are then broadcast to the network. They come as browser extensions, mobile or desktop apps, or hardware devices that keep keys offline; custodial 'wallets' at exchanges instead entrust keys to the platform.
    Failure modes: Phishing sites and malicious approvals trick users into signing transactions that drain their accounts; lost keys or seed phrases mean permanent, unrecoverable loss since there is no password reset.
    Misconceptions: Coins are not stored 'in' the wallet — only the keys are; switching wallet apps does not move funds. A custodial exchange balance is an IOU, not self-custody of the underlying asset.
    Example: You open MetaMask, which derives your address 0x5e97...a120 from your private key; when you send 0.5 ETH, the wallet signs the transaction with that key and broadcasts it, and the ledger — not the wallet — records the new balance.
    Aliases: crypto wallet

    Private key #

    A private key is a secret 256-bit number that controls an externally owned blockchain account: whoever knows it can sign transactions and spend the account's funds, so it must never be revealed.
    Intuition: The private key is the one true password to your coins — there is no recovery desk if it leaks or is lost.
    Mechanics: Wallets generate a random private key (64 hex characters); the corresponding public key is derived via elliptic-curve multiplication (ECDSA/secp256k1 on Ethereum), and the address is the last 20 bytes of the Keccak-256 hash of the public key. Signing a transaction with the private key proves authorization without revealing the key.
    Failure modes: Key theft (malware, phishing, insecure backups) gives irreversible control of funds; key loss is final because no one can regenerate a private key from an address — the derivation is one-way.
    Misconceptions: A private key cannot be recovered from the public address — reversing the hash or the elliptic-curve multiplication is computationally infeasible. Changing a wallet password does not change or protect an already-leaked key.
    Example: A private key looks like ffffffff...415f (64 hex chars); exposing it once in a screenshot or cloud note lets anyone sweep the account's entire balance in a single signed transaction.
    public_key = private_key × G (elliptic curve point multiplication with generator G); address = last 20 bytes of Keccak256(public_key).
    Aliases: secret key

    Public key #

    A public key is the openly shareable half of an account's cryptographic key pair, derived one-way from the private key and used by the network to verify signatures and derive the account address.
    Intuition: It is like your email address for money: anyone can know it and send you funds, but only the matching private key can spend them.
    Mechanics: The public key is computed from the private key by elliptic-curve multiplication, which is infeasible to reverse. On Ethereum, the account address is the last 20 bytes of the Keccak-256 hash of the public key; when a signed transaction is broadcast, nodes recover the public key from the signature to prove the sender's identity.
    Failure modes: Sharing a public key or address is safe for receiving funds, but address reuse and public on-chain history destroy privacy since anyone can trace all associated activity.
    Misconceptions: A public key is not the same as an address — the address is a hash of the public key, and the public key itself is only revealed on-chain when the account first sends a transaction.
    Example: An Ethereum address such as 0x5e97870f263700f46aa00d967821199b9bc5a120 is derived by hashing the account's public key; anyone can verify that a transaction signed by the matching private key genuinely came from that account.
    public_key = private_key × G (one-way elliptic curve multiplication); address = last 20 bytes of Keccak256(public_key), prefixed with 0x.

    Seed phrase #

    A seed phrase (recovery phrase) is a human-readable list of typically 12 or 24 words that encodes the entropy from which all of a wallet's private keys are deterministically derived, serving as the master backup for the wallet.
    Intuition: It is the master key written in words: anyone who reads it owns everything the wallet controls, forever.
    Mechanics: Wallets following standards such as BIP-39 generate the phrase from random entropy and derive the entire key hierarchy from it, so re-entering the phrase on any compatible wallet regenerates the same accounts. Wallet providers instruct users to write it down offline because it is the only recovery path.
    Failure modes: Phishing attacks that ask users to 'verify' their seed phrase are the dominant wallet-drain vector; storing it in cloud notes, photos or email makes remote theft trivial, and losing it makes funds unrecoverable.
    Misconceptions: A seed phrase cannot be changed after the fact — if it leaks, the only remedy is moving funds to accounts derived from a new phrase. The wallet app's password does not protect a leaked phrase.
    Example: A 12-word phrase like 'there aeroplane curve vent formation doge possible product distinct under spirit lamp' can regenerate every account in the wallet on a new device; whoever types it into any wallet software gains full control of the funds.
    Aliases: recovery phrase, mnemonic phrase, backup phrase

    Smart contract #

    A smart contract is a program deployed to a blockchain — a collection of code (functions) and data (state) at a specific address — that executes automatically and exactly as written when called by a transaction.
    Intuition: A vending machine for logic: given the right inputs and fee, a guaranteed, unstoppable output, with no operator able to intervene.
    Mechanics: Developers compile code (e.g. Solidity) to EVM bytecode and deploy it via a transaction; the contract then exists as an account type with a balance and storage but no private key. Users and other contracts invoke its functions by sending transactions that pay gas; execution is deterministic and replicated by every node, and deployed code cannot be altered by default.
    Failure modes: Bugs are immutable — exploits like re-entrancy or logic errors can drain contracts with no way to patch or reverse; contracts cannot fetch off-chain data themselves and inherit the risks of whatever oracle they trust.
    Misconceptions: Smart contracts are neither 'smart' nor legal contracts — they only execute code, cannot interpret intent, and cannot access real-world data without an oracle. 'Code is law' fails badly when the code has bugs.
    Example: A simple contract might hold 100 cupcake balances and release one to any caller who sends 1 ETH; once deployed, no one — including its creator — can change the 1 ETH price or freeze the cupcakes.
    Aliases: contract

    Gas fee #

    A gas fee is the payment, denominated in the chain's native currency, that compensates the network for the computational resources a transaction consumes, priced per unit of 'gas' — the protocol's measure of computational effort.
    Intuition: Gas is the meter on the world's shared computer: every operation you run ticks up a bill you must pay, whether or not the transaction succeeds.
    Mechanics: Fee = gas units used × (base fee + priority fee). The base fee is set by the protocol per block (adjusting up to ±12.5% based on demand against a target block size) and is burned; the priority fee (tip) goes to the validator to incentivize inclusion. Users can cap total spend with maxFeePerGas, and unused gas is refunded.
    Failure modes: Demand spikes can push fees above the value of small transactions, pricing users out; setting a gas limit too low causes the transaction to run out of gas, fail, and still consume the fee.
    Misconceptions: Gas fees are not paid to a company — the base fee is burned and only the tip reaches the validator. A failed transaction still costs gas because computation was performed.
    Example: Sending 1 ETH with a base fee of 10 gwei and a 2 gwei tip costs 21,000 × 12 gwei = 0.000252 ETH; the sender pays 1.000252 ETH total, the base fee of 0.00021 ETH is burned, and the validator keeps the 0.000042 ETH tip.
    gas fee = gas_used × (base_fee + priority_fee); e.g. 21,000 × (10 + 2) gwei = 252,000 gwei = 0.000252 ETH.
    Aliases: transaction fee, network fee

    Block space #

    Block space is the finite capacity of each block to include transactions, measured in gas (Ethereum) or bytes/weight (Bitcoin); it is the scarce resource that gas markets price.
    Intuition: Each block is a truck with a fixed cargo hold leaving at fixed intervals — when more freight shows up than fits, shippers bid up the price of space.
    Mechanics: Ethereum blocks target half the block gas limit (e.g. 15M of a 30M limit) and can expand to the limit under demand; the base fee rises or falls up to 12.5% per block to push usage back toward the target. Because each transaction consumes gas against this cap, demand for block space directly sets fee levels.
    Failure modes: Sustained congestion makes the chain unusable for low-value transactions and invites MEV bidding wars; raising the block limit trades decentralization for capacity by increasing node hardware requirements.
    Misconceptions: Block space scarcity is a design choice, not an accident — unbounded blocks would centralize validation. High fees signal demand for space, not a broken fee mechanism.
    Example: If an NFT mint fills blocks to the 30M gas limit for several blocks in a row, the base fee compounds upward by 12.5% per full block, and a simple transfer that cost 10 gwei can jump past 200 gwei within minutes.
    Aliases: blockspace

    Mempool #

    The mempool (memory pool) is each node's local holding area for valid broadcast transactions that have not yet been included in a block; block producers select transactions from it, typically by fee offered.
    Intuition: It is the public waiting room for transactions — and because everyone can read it, predators can see your trade before it executes.
    Mechanics: When a user broadcasts a transaction, each receiving node validates it, adds it to its local mempool and gossips it to peers. Validators pick transactions (usually highest priority fee first) when building a block; transactions can linger, be replaced by higher-fee versions, or be dropped. Public visibility of pending transactions enables front-running and sandwich attacks.
    Failure modes: Public mempool visibility lets searchers front-run or sandwich pending trades; congestion can leave low-fee transactions pending indefinitely, and private relay channels used to avoid this reintroduce centralization.
    Misconceptions: The mempool is not a single global queue — each node has its own mempool and they can differ. Inclusion is not FIFO; ordering is at the block builder's discretion and usually fee-driven.
    Example: A 100 ETH Uniswap buy sits in the mempool for ~12 seconds before inclusion; a sandwich bot sees it, buys the same token in front of it, lets the victim's trade push the price up, and sells immediately after for a profit.
    Aliases: transaction pool, txpool

    Transaction finality #

    Transaction finality is the point at which a transaction's inclusion in the chain becomes irreversible — on proof-of-stake Ethereum, when the block containing it sits under checkpoints justified and finalized by ≥2/3 of staked ETH, so reversal would require burning at least one-third of all stake.
    Intuition: Finality is when 'pending' becomes 'set in stone' — before it, the chain can still be rewritten; after it, reversal would cost attackers billions.
    Mechanics: Ethereum divides time into 32-slot epochs; validators vote on checkpoint pairs, and a checkpoint with a two-thirds supermajority becomes justified, then finalized when the next checkpoint is justified (~2 epochs, ≈13 minutes). In proof-of-work chains finality is only probabilistic: confidence grows with each confirmation but never becomes absolute.
    Failure modes: If >1/3 of stake goes offline or votes against finality, the chain stalls and the inactivity leak must burn dissenting stake to recover; bridges and exchanges that credit deposits before finality are exposed to reorg double-spends.
    Misconceptions: One confirmation is not finality — recent blocks can be reorganized. PoS finality is economic, not absolute: reversal is possible in principle if attackers are willing to be mass-slashed.
    Example: An exchange crediting ETH deposits waits for finalization (~15 minutes): reverting a finalized deposit would require an attacker to get at least one-third of all staked ETH destroyed, an economically irrational cost.
    Aliases: finality

    Confirmation #

    A confirmation is the inclusion of a transaction in a mined/validated block; each additional block built on top counts as another confirmation and exponentially reduces the probability that the transaction is reversed.
    Intuition: Each confirmation is another layer of concrete poured over your transaction — one layer can be broken through, six is conventional vault-grade.
    Mechanics: In proof-of-work chains, the probability that an attacker catches up to the honest chain decays exponentially with the number of confirmations (Nakamoto's analysis), so receivers wait for N blocks (conventionally 6 for Bitcoin, ≈60 minutes) before treating payment as safe. On proof-of-stake Ethereum, confirmations culminate in explicit finality after two epochs.
    Failure modes: Accepting zero-confirmation transactions exposes the receiver to double-spends; during chain reorganizations, even confirmed transactions can temporarily be dropped back to pending.
    Misconceptions: 'Confirmed' does not mean 'irreversible' on PoW chains — it is a confidence gradient, which is why high-value transfers wait for more confirmations. The 6-block rule is a convention, not a protocol guarantee.
    Example: A merchant accepting a $50,000 BTC payment waits for 6 confirmations (~1 hour) because reversing 6 blocks would require an attacker to privately out-mine the honest network for an hour, an astronomically unlikely feat at honest-majority hash rate.
    Aliases: block confirmation

    Layer 1 #

    A layer 1 (L1) is the base blockchain network itself — such as Ethereum or Bitcoin — that provides its own consensus, data availability and settlement, and on which layer-2 systems anchor their security.
    Intuition: The L1 is the bedrock courthouse of record: slower and expensive, but its rulings are final and everything built above ultimately defers to it.
    Mechanics: L1s execute and validate all transactions directly on the base chain, so throughput is bounded by what ordinary nodes can process; scaling the L1 itself (onchain scaling) requires protocol changes. Layer-2 rollups move execution off the L1 but post transaction data or proofs back to it, inheriting its security and finality.
    Failure modes: L1 congestion prices out users and pushes activity to less secure venues; a consensus failure or successful attack on the L1 undermines every layer 2 anchored to it.
    Misconceptions: Not every chain with cheap fees is 'just an L2' — sidechains with their own consensus are separate L1-style systems that do not inherit Ethereum's security. L1 scaling by simply raising block size sacrifices decentralization.
    Example: Ethereum Mainnet is the L1 that processes ~15M gas of target block usage per 12-second slot; Arbitrum posts its transaction batches to Ethereum so that, even if Arbitrum's operator vanishes, users can reconstruct state and exit via the L1.
    Aliases: base layer, L1, mainnet

    Layer 2 #

    A layer 2 (L2) is a protocol built on top of a layer-1 blockchain that handles transactions off the base chain to increase speed and throughput while deriving its security from the L1's consensus — chiefly via rollups, state channels, or related constructions.
    Intuition: An L2 is an express lane that does the fast driving elsewhere but files the paperwork at the L1 courthouse, so the L1's security still backs every transaction.
    Mechanics: Users transact on the L2 (usually via an operator called a sequencer); the L2 batches transactions and posts compressed data and/or proofs to L1 contracts. Rollups (optimistic or zero-knowledge) anchor data availability and dispute resolution on the L1; true L2s can be exited trustlessly using the on-chain data, unlike sidechains.
    Failure modes: Most L2s run a single centralized sequencer that can censor or reorder transactions and is a liveness single point of failure; bridge contracts holding L1 escrow are high-value exploit targets.
    Misconceptions: Not everything marketed as L2 inherits L1 security — sidechains and validiums secure their own data and are weaker. Cheap L2 fees do not mean the L2 is trustless; sequencer centralization is the norm today.
    Example: On Arbitrum (an optimistic rollup), a token swap costs a few cents instead of several dollars on Ethereum; the batch containing it is posted to Ethereum, and withdrawals to L1 finalize after a ~7-day challenge window unless a fast-exit liquidity provider is used.

    Rollup #

    A rollup is a layer-2 scaling solution that executes transactions off the layer-1 chain and then posts the transaction data (and a state commitment) back to the L1, so that the L1's consensus secures and finalizes the rolled-up state.
    Intuition: A rollup runs thousands of transactions on a fast side system, then drops one summarized receipt onto Ethereum — the L1 keeps the evidence needed to check or reconstruct everything.
    Mechanics: An operator batches offchain transactions, executes them, and publishes compressed data (as calldata or blobs) plus a new state root to an L1 rollup contract. Optimistic rollups assume validity and allow fraud challenges; zero-knowledge rollups attach a validity proof. Because the data lives on L1, anyone can reconstruct the rollup state and force exits.
    Failure modes: Centralized sequencers can censor or reorder transactions; if data posting stops or the prover/fraud-proof system fails, users may be unable to exit; upgrade keys and admin controls on rollup contracts introduce trust assumptions.
    Misconceptions: Posting data to L1 does not mean the L1 re-executes the transactions — execution happens offchain and the L1 stores evidence. Rollup transactions are not 'instantly final' — they finalize only when the L1 accepts the batch (and, for optimistic rollups, the challenge window closes).
    Example: An Ethereum block targeting 15M gas can carry roughly 78,000 compressed rollup transactions per block in theory; a rollup batching 2,000 transfers per post gives users cent-level fees while Ethereum's validators secure the data.

    Optimistic rollup #

    An optimistic rollup is a layer-2 rollup that assumes offchain transaction batches are valid by default and relies on a fraud-proof scheme: anyone can challenge a posted state transition during a challenge period, and proven fraud reverts the batch and slashes the operator's bond.
    Intuition: It is an honor system with a bounty: transactions are accepted unless someone can prove cheating within a week, and the cheater's deposit pays for the mistake.
    Mechanics: A sequencer batches transactions, posts them to Ethereum (calldata/blobs) with a new state root, and a challenge window (typically ~7 days) opens. Challengers re-execute the disputed step via an interactive bisection protocol settled by an L1 verifier contract; a successful fraud proof rolls back the invalid state and slashes the operator. Withdrawals to L1 must wait out the challenge period.
    Failure modes: Security rests on at least one honest watcher submitting fraud proofs — if all watchers fail or are censored, a malicious operator can steal funds; the 7-day withdrawal delay harms UX and pushes users toward trusted fast-exit bridges; centralized sequencers can censor.
    Misconceptions: Optimistic rollups are not 'less secure versions of Ethereum' in the fraud-proof model — one honest node suffices to defend correct state — but most deployments still have training wheels (upgradeable contracts, permissioned provers). 'Optimistic' refers to the validity assumption, not speed.
    Example: A user withdrawing 5 ETH from Arbitrum to Ethereum initiates the exit on L2, waits the ~7-day challenge period, then finalizes on L1; alternatively a liquidity provider fronts the 5 ETH immediately on L1 for a fee.
    Aliases: OR, optimistic roll-up

    Zero-knowledge rollup #

    A zero-knowledge rollup (ZK-rollup) is a layer-2 rollup that executes transactions offchain and submits a succinct cryptographic validity proof (ZK-SNARK or ZK-STARK) to the layer-1 contract, which verifies the proof and finalizes the new state without re-executing the transactions.
    Intuition: Instead of 'trust me, challenge me if I cheat' (optimistic), a ZK-rollup posts mathematical proof that every transaction in the batch was executed correctly — verified on L1 in one step.
    Mechanics: The operator batches transactions, computes new state roots and generates a validity proof attesting that the state transition followed the rules; the L1 verifier contract checks the proof and updates the canonical state root. Because validity is proven up front, withdrawals finalize as soon as the proof is verified, with no challenge period; transaction data is still posted as calldata for reconstructibility.
    Failure modes: Proof generation is computationally expensive and often centralized, and proving systems with trusted setups (many SNARKs) break if the setup's 'toxic waste' leaks; bugs in the circuit or verifier contract can silently accept invalid state transitions.
    Misconceptions: ZK-rollups do not inherently provide privacy — 'zero-knowledge' here proves correctness of computation, and most ZK-rollups publish full transaction data. They are not automatically EVM-compatible; general-purpose zkEVMs are much harder than simple payment circuits.
    Example: On zkSync Era, a batch of transfers is finalized on Ethereum minutes after the operator submits its validity proof, whereas the same withdrawal on an optimistic rollup would sit in a 7-day challenge window.
    Aliases: ZK-rollup, zkRollup, validity rollup

    Bridge #

    A blockchain bridge is a mechanism that transfers assets, messages or arbitrary data between otherwise isolated blockchain networks, typically by locking or burning assets on the source chain and minting a representation on the destination chain.
    Intuition: Bridges are ferries between islands that cannot naturally talk to each other — but the ferry company is often the weakest security link in the whole trip.
    Mechanics: Common designs are lock-and-mint (escrow asset on chain A, mint wrapped asset on chain B), burn-and-mint, and liquidity-network atomic swaps. Trustless bridges rely on the connected chains' own validation (light clients, fraud/validity proofs); trusted bridges introduce external validator sets, multisigs or oracles that users must trust not to collude.
    Failure modes: Bridges account for the largest DeFi hacks: smart contract flaws (e.g. the Wormhole exploit), validator collusion in trusted designs, and depegged wrapped assets can all make bridged tokens unbacked; systemic risk compounds because wrapped assets are used as collateral elsewhere.
    Misconceptions: A wrapped token on another chain is not the same asset — it is an IOU backed by the bridge's custody. 'Trustless' bridges still carry smart contract risk, and native (canonical) L2 bridges are far safer than third-party multisig bridges.
    Example: To move ETH to Arbitrum via its native bridge, you deposit ETH into the L1 bridge contract and an equivalent amount is credited on L2; using a third-party multisig bridge instead means trusting that a small validator set will not collude to steal the escrow.
    Aliases: blockchain bridge, cross-chain bridge

    Oracle #

    A blockchain oracle is a service that sources, verifies and transmits off-chain data (prices, events, computation results) onto the blockchain so that smart contracts — which cannot access external data themselves — can act on it.
    Intuition: Contracts are sealed in a deterministic box and can't browse the internet; the oracle is the courier that slips verified notes under the door.
    Mechanics: An on-chain oracle contract receives data requests; off-chain oracle nodes query APIs or data sources, reach agreement (e.g. via median aggregation across many nodes, as in Chainlink price feeds), and post the result on-chain where any contract can read it. Decentralized oracle networks use multiple independent nodes and sources plus staking/reputation to resist manipulation.
    Failure modes: If the oracle reports a wrong or stale price, lending protocols liquidate solvent users or let attackers drain pools with mispriced collateral; single-source or centralized oracles are one hack or outage away from corrupting every dependent contract ('the oracle problem').
    Misconceptions: Oracles do not make off-chain data trustless — they shift trust to the oracle network's aggregation and incentives. A decentralized oracle with many nodes but one upstream data source still has a single point of failure.
    Example: Aave reads a Chainlink ETH/USD price feed to value collateral; if the feed briefly reported ETH at half its true price, thousands of loans would instantly fall below their liquidation thresholds through no fault of borrowers.
    Aliases: blockchain oracle, price oracle, price feed
